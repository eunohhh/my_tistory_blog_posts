<h1>JWT vs 세션, 그리고 JWK의 정체</h1>
<h3 data-ke-size="size23">TL;DR</h3>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">"JWT가 죽은 게 아니라, JWT를 <b>브라우저 세션 관리 도구로 쓰던 오용이 교정</b>된 것."<br />다시 상기하자, 쿠키 vs JWT는 대립 축이 아님, 쿠키는 전송 수단, JWT는 토큰 포맷.</p>
</blockquote>
<h2 data-ke-size="size26">발단</h2>
<p data-ke-size="size16">better-auth, Supabase Auth 등 최근 인증 솔루션들이 JWT(JWK)를 지원하면서도<br />기본값은 쿠키+세션인 걸 보고 의문이 생겼다. 분명 몇 년 전엔 "JWT로 통일" 분위기였는데?</p>
<h2 data-ke-size="size26">1. 인증 트렌드는 실제로 한 바퀴 돌았다</h2>
<h3 data-ke-size="size23">JWT 전성기 (~2015&ndash;2021)</h3>
<p data-ke-size="size16">SPA + REST API 분리 아키텍처의 유행과 정확히 겹친다.<br />프론트와 백이 다른 도메인, "stateless라 스케일링에 좋다"는 마케팅,<br />튜토리얼마다 복붙되던 localStorage 저장 패턴.</p>

<h3 data-ke-size="size23">회귀의 결정타 (2022&ndash;2025)</h3>
<p data-ke-size="size16">Next.js App Router/RSC, Remix 등 <b>서버 렌더링 회귀</b>로 프론트와 백이 같은 first-party 서버가 됨.<br />이 구조에서는 httpOnly 쿠키가 자연스럽고(CSRF는 SameSite로 대부분 해결),<br />클라이언트가 토큰을 직접 다룰 이유가 사라짐. Lucia 작자의 세션 기반 주장,<br />better-auth의 쿠키+DB 세션 기본값이 이 맥락.</p>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">쿠키는 <b>전송 수단</b>, JWT는 <b>토큰 포맷</b>.<br />예로 Supabase는 내부적으로 여전히 JWT 기반(access token이 JWT)이지만,<br />저장/전송은 httpOnly 쿠키로 하는 하이브리드다.</p>
</blockquote>
<h3 data-ke-size="size23">현재 수렴된 컨센서스</h3>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>first-party 웹앱 세션</b> &rarr; httpOnly 쿠키 (내용물은 opaque 세션 ID든 짧은 수명 서명 토큰이든)</li>
<li><b>서비스 간 통신 / 서드파티 API / OIDC 연합 인증</b> &rarr; JWT가 여전히 표준, 대체재 없음</li>
<li><b>하이브리드</b> &rarr; 짧은 수명(수분~1시간) JWT access + DB 추적 refresh/세션. 검증은 stateless의 이점, 폐기는 refresh 시점에 가능</li>
</ul>
<h2 data-ke-size="size26">2. JWK가 정확히 뭔가</h2>
<blockquote data-ke-style="style1">
<p data-ke-size="size16"><b>JWK(JSON Web Key) = 암호화 키를 JSON으로 표현하는 포맷.</b><br />토큰도 프로토콜도 아니고, PEM 파일의 JSON 버전이라고 생각하면 된다.</p>
</blockquote>
<pre class="json"><code>{
  "kty": "RSA",
  "kid": "key-2026-01",
  "use": "sig",
  "alg": "RS256",
  "n": "0vx7agoebGcQ...",
  "e": "AQAB"
}</code></pre>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><code>kty</code>: 키 종류 (RSA, EC, OKP...)</li>
<li><code>kid</code>: key ID &mdash; 여러 키 중 어느 것으로 검증할지 식별</li>
<li><code>n</code>, <code>e</code>: RSA modulus / exponent, 수학적 키 재료 자체</li>
<li><code>use</code> / <code>alg</code>: 서명용 여부, 알고리즘</li>
</ul>

<h3 data-ke-size="size23">검증 흐름</h3>
<ol style="list-style-type: decimal;" data-ke-list-type="decimal">
<li>JWT 헤더에서 <code>kid</code>를 읽는다</li>
<li>JWKS 엔드포인트(예: <code>https://&lt;project&gt;.supabase.co/auth/v1/.well-known/jwks.json</code>)에서 같은 <code>kid</code>의 JWK를 찾는다 (보통 캐싱)</li>
<li>그 공개키로 서명을 검증한다</li>
</ol>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">발급자가 새 키를 JWKS에 추가하고 새 토큰부터 새 키로 서명하면,<br />검증자들은 코드 변경 없이 <code>kid</code> 매칭만으로 따라온다.<br />Google 로그인 검증 시 <code>googleapis.com/oauth2/v3/certs</code>를 가져오는 것도 같은 패턴.</p>
</blockquote>
<h2 data-ke-size="size26">3. HS256 &rarr; RS256: 기밀성이 아니라 무결성+증명</h2>
<p data-ke-size="size16">처음에 "대칭키+비대칭키 하이브리드 암호화(ex: TLS)랑 같은 거네"라고 생각했는데,<br /><b>동기는 같고 메커니즘은 다르다</b>.</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>하이브리드 암호화: 비대칭으로 대칭키 교환 &rarr; 데이터는 빠른 대칭키로 암호화. 두 방식의 <b>조합</b>, 목적은 <b>기밀성</b></li>
<li>JWT의 HS256 &rarr; RS256: 대칭 MAC을 비대칭 서명으로 <b>대체</b>. 목적은 <b>무결성 + 발급자 증명</b> (payload는 base64라 누구나 읽을 수 있음. 숨기는 게 아니라 "위조되지 않았음"을 보장)</li>
</ul>
<p data-ke-size="size16">공유하는 뿌리는 <b>"대칭키는 공유해야 해서 관리가 안 된다"는 키 배포 문제</b>:</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>HS256: 검증자 전원이 secret 보유 &rarr; 하나만 털려도 <b>토큰 위조 가능</b> (secret으로 서명까지 할 수 있으므로)</li>
<li>RS256: 공개키가 유출돼도 검증밖에 못 함 &rarr; 발급 권한은 발급자에게만</li>
</ul>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">RS256 = RSASSA-PKCS1-v1_5 서명 + SHA-256 해시. ES256이면 RSA 대신 타원곡선(ECDSA P-256).</p>
</blockquote>
<h2 data-ke-size="size26">4. Supabase가 JWT를 쓸 수밖에 없는 이유: 분산 아키텍처</h2>
<p data-ke-size="size16">생각해보면 Supabase는 단일 서버가 아니라 <b>별도 컴포넌트들의 묶음</b>이다.<br />로컬에서 <code>supabase start</code> 하면 Docker 컨테이너가 대여섯 개 뜨는 이유.</p>
<pre class="coffeescript"><code>Kong (API 게이트웨이) ── 모든 요청의 입구
 ├─ GoTrue        /auth/v1/*      인증 서버 (Go)
 ├─ PostgREST     /rest/v1/*      테이블 &rarr; REST API
 ├─ Realtime      /realtime/v1/*  WebSocket 구독 (Elixir)
 ├─ Storage API   /storage/v1/*
 └─ PostgreSQL    ── 모두가 공유하는 DB</code></pre>
<p data-ke-size="size16">요청마다 각 컴포넌트가 Auth 서버에 "이 세션 유효해?"라고 물어보면 병목<br />&rarr; <b>각자 토큰만 보고 로컬 검증</b>해야 함 &rarr; JWT의 원래 용도.</p>
<p data-ke-size="size16">Supabase도 원래는 HS256 공유 secret이 기본이었고,<br />JWKS 기반 비대칭 검증은 비교적 최근에 추가&middot;권장되기 시작했다고 한다..</p>
<h3 data-ke-size="size23">GoTrue의 정체</h3>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>Netlify가 만든 Go 기반 인증 마이크로서비스를 Supabase가 포크 &rarr; 현재는 <code>supabase/auth</code> 리포로 독자 발전, 공식 명칭은 Supabase Auth</li>
<li><code>auth</code> 스키마는 <b>GoTrue의 전용 저장소</b>일 뿐, 행위의 주체가 아니다</li>
<li>회원가입 시: GoTrue가 <code>auth.users</code>에 row 쓰기 &rarr; SMTP 인증 메일 발송 &rarr; 확인 클릭 받아 <code>email_confirmed_at</code> 채움 &rarr; JWT 서명&middot;발급. OAuth 리다이렉트 왕복도 GoTrue 담당</li>
<li>Supabase가 <code>auth</code> 스키마 직접 수정을 경고하는 이유 = <b>남의 서비스 내부 상태</b>이기 때문</li>
</ul>
<h3 data-ke-size="size23">RLS와 연결되는 지점</h3>
<p data-ke-size="size16">PostgREST는 요청의 JWT를 <b>스스로 검증</b>하고, payload의 <code>sub</code>(user ID)와 <code>role</code>을 PostgreSQL 세션 변수로 설정 &rarr; RLS 정책이 <code>auth.uid()</code>로 그 값을 읽어 행 단위 접근 제어. GoTrue는 <b>발급</b>에만 등장하고 <b>검증은 분산 처리</b>.</p>
