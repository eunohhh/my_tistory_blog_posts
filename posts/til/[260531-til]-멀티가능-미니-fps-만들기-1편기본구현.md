<h1>멀티플레이어 미니 FPS 만들기 1편(기본편)</h1>
<p data-ke-size="size16">어두운 아레나에서 손전등으로 앞을 비추며 페인트볼로 눈싸움하는, 최대 3인용 웹 FPS를 0에서 끝까지 만든 기록.<br />과정을 잊지 않고자 기록하는, 남이 읽기엔 불친절한 기록물.</p>
<h2 data-ke-size="size26">결과물</h2>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>배포: <a href="https://eunoh.top/tests/mini-fps">https://eunoh.top/tests/mini-fps</a></li>
<li>백엔드: 권위 게임 서버 (Node + ws, Rapier 물리, 30Hz 틱)</li>
<li>프론트: 클라이언트 (Next 16 / React 19 / three.js &middot; R3F &middot; drei)</li>
</ul>
<h2 data-ke-size="size26">어떤 게임인가</h2>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>컨셉</b>: 총기 난사가 아니라 <i>눈싸움/페인트볼</i>. 페인트볼이 포물선을 그리며 날아가고, 회피가 가능하다.</li>
<li><b>분위기</b>: 거의 검정에 가까운 아레나. 각 플레이어는 손전등을 들고 앞을 비춘다. 어둠 속에서 다른 사람의 손전등 불빛이 휘청거리며 움직이는 게 보인다.</li>
<li><b>규칙</b>: 체력 100, 페인트볼 한 발에 10 데미지(10발에 사망), 사망 시 랜덤 위치 즉시 리스폰, 10분 매치 후 점수판.</li>
</ul>
<h2 data-ke-size="size26">두 문서로 나눈 이유</h2>
<p data-ke-size="size16">한 번에 다 만들지 못했다. 그럴 수밖에 없었다.</p>
<p data-ke-size="size16"><br />처음엔 어떻게 만드는지를 모르는 상태에서 한 단계씩 빌드업했고,<br />그게 어느 정도 돌아가게 된 뒤에야 돌아가는 코드를 진짜 게임답게 다듬을 수 있었다.</p>
<p data-ke-size="size16">두 단계는 사고방식이 다르다.</p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16">앞은 "이걸 어떻게 만들지?"의 연속이었고,</p>
<p data-ke-size="size16">뒤는 "이걸 어떻게 더 견고하게 만들지?"의 연속이었다. 그래서 문서도 나눴다.</p>
<p data-ke-size="size16">&nbsp;</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>
<ol style="list-style-type: decimal;" data-ke-list-type="decimal">
<li>이 문서 - 기본구현편: 0에서 게임 네트워킹을 배우며 만든 과정. 각 단계의 <i>왜</i>와 <i>함정</i>이 핵심.</li>
</ol>
</li>
<li>
<ol style="list-style-type: decimal;" start="2" data-ke-list-type="decimal">
<li>운영편: 만든 걸 멀티룸&middot;EC2 배포&middot;맵 권위화&middot;자연 지형으로 다듬은 과정. 기술적 결정과 트레이드오프의 기록.</li>
</ol>
</li>
</ul>
<h2 data-ke-size="size26">핵심 아키텍처 한눈에</h2>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>서버 권위 + 클라언트 예측</b>: 서버가 30Hz로 시뮬레이션(SSOT), 클라는 입력 즉시 예측 후 서버 스냅샷(15Hz)으로 보정(reconciliation).</li>
<li><b>결정론</b>: 예측과 재시뮬이 일치하려면 클라/서버의 시뮬 로직(이동&middot;중력&middot;점프)과 충돌 지오메트리(Rapier 동일 버전 + 동일 맵 데이터)가 <i>비트 단위로 동일</i>해야 한다.</li>
<li><b>단일 권위 데이터</b>: 맵을 서버가 정의해 클라에 전송. 렌더&middot;충돌&middot;예측이 한 소스에서 파생된다.</li>
</ul>

<h2 data-ke-size="size26">전체 흐름</h2>

<h2 data-ke-size="size26">1. 시작 전 결정들</h2>
<h3 data-ke-size="size23">Nest를 재활용할까?</h3>
<p data-ke-size="size16">EC2에 NestJS 백엔드가 이미 떠 있었다.<br />처음엔 "Nest 리소스가 있으니 거기서 시작하자"였는데, 한 단계씩 따져보니 결론이 뒤집혔다.</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>같은 Nest 앱에 모듈 추가 &rarr; 재활용 최대, 격리 최소 (게임 틱 루프가 API 트래픽과 한 프로세스)</li>
<li>별도 프로세스 + Nest &rarr; <b>어정쩡함</b> (재활용도 격리도 어중간)</li>
<li>별도 프로세스 + 순수 Node/ws &rarr; 재활용은 인프라(EC2) 레벨, 격리 최대 ✓</li>
</ul>
<p data-ke-size="size16"><b>교훈</b>: "재활용할 리소스"가 <i>Nest 코드베이스</i>가 아니라 <i>EC2 인스턴스</i>라는 걸 깨닫자 답이 명확해졌다.<br />게임 서버는 tight loop라서 Nest의 DI&middot;모듈 추상화가 오히려 방해된다.</p>
<h3 data-ke-size="size23">페인트볼 컨셉을 택한 이유</h3>
<p data-ke-size="size16">애초에 만들고 싶었던 건, <i>어두운 아레나 + 손전등 + 눈싸움</i>.<br />그런데 이게 사실 미니 프로젝트에 <b>훨씬 유리한 선택</b>이었다.</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>총기 raycast 방식(CS, Valorant): 발사 즉시 광선. 정확한 히트 판정에 <b>Lag Compensation 필수</b> - 서버가 RTT만큼 과거로 모든 플레이어를 되돌려 판정. 진입장벽 큼.</li>
<li>투사체 방식(페인트볼): 발사 후 시간을 두고 날아감. <b>Lag Compensation 불필요</b> - 투사체가 서버 시간으로 계속 진행하고, 충돌 시점에 거기 있던 사람이 맞는다. 자연스럽다.</li>
</ul>
<p data-ke-size="size16"><b>교훈</b>: 컨셉이 곧 기술 난이도를 결정한다. 만들고 싶은 그림이 <i>마침</i> 더 단순한 구현으로 이어진 건 운이 좋았다.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">2. 게임 네트워킹의 핵심 개념</h2>
<p data-ke-size="size16">빌드업 전에 머리에 넣어둔 표준 모델.<br />Valve의 Source 엔진 모델이 사실상 표준이고, "Source Multiplayer Networking" 문서가 가장 깔끔한 정리.</p>
<ol style="list-style-type: decimal;" data-ke-list-type="decimal">
<li><b>Client-Side Prediction</b> - 클라이언트가 입력 즉시 자기 캐릭터를 움직인다. 서버 응답을 안 기다린다.</li>
<li><b>Server Reconciliation</b> - 서버가 "네 입력 N번까지 처리한 결과는 이거야"라고 알려주면, 클라이언트가 그 시점으로 되돌린 뒤 미적용 입력들을 다시 시뮬레이션한다.</li>
<li><b>Entity Interpolation</b> - <i>다른</i> 플레이어들은 서버 스냅샷 사이를 100~150ms 늦춰 보간해 부드럽게 그린다.</li>
<li><b>Lag Compensation</b> - 서버가 슈터의 지연만큼 과거로 타겟을 되돌려 히트 판정. <b>이 프로젝트는 페인트볼(투사체)이라 안 썼다.</b></li>
</ol>
<p data-ke-size="size16">이 네 가지가 왜 필요한지는 머리로 아는 것과 <i>직접 끊기는 화면을 보는 것</i>이 천지차이였다.<br />그래서 일부러 예측&middot;보간을 <i>끄고 시작</i>해서 끔찍한 끊김을 먼저 봤다.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">3. 서버 골격 (Step 1~6)</h2>
<h3 data-ke-size="size23">raw WebSocket, Nest 게이트웨이 안 씀</h3>
<p data-ke-size="size16"><code>ws</code> 패키지만으로 시작. 의존성은 <code>ws</code> + <code>tsx</code>(개발용) + 타입 정도.<br />Nest로 같은 걸 짜면 모듈&middot;게이트웨이&middot;데코레이터 합쳐 <i>더 길어진다</i>. 진입점이 30줄도 안 됐다.</p>
<h3 data-ke-size="size23">discriminated union + switch never 안전망</h3>
<p data-ke-size="size16">모든 메시지를 <code>{ type: '...' , ... }</code> 형태의 discriminated union으로 정의하고,<br />라우터에서 <code>switch (msg.type)</code> + <code>default</code>에 <code>const _exhaustive: never = msg</code>를 뒀다.</p>
<pre class="actionscript"><code>// 새 메시지 타입 추가 후 핸들러 빼먹으면 &rarr; 여기서 컴파일 에러
default: {
  const _exhaustive: never = msg
}</code></pre>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>교훈</b>: 게임 서버는 메시지 종류가 폭발.. 수준이다(input, snapshot, hello, fire, hit, kill, ...).<br />문자열 비교로 분기하면 30분 만에 무너진다.<br />never 패턴이 <i>타입 추가 시 핸들러 누락을 컴파일 타임에 잡아주는</i> 안전망이 됐다.</p>
<h3 data-ke-size="size23">self-correcting tick loop와 death spiral 방지</h3>
<p data-ke-size="size16"><code>setInterval</code>은 정확한 30Hz를 보장 안 한다.<br />다른 이벤트에 밀리면 틱이 늦는다. 그래서 <i>밀린 만큼 따라잡는</i> self-correcting 루프를 썼다.</p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16">다만 <i>한 번에 너무 많이 따라잡으면</i> 위험하다. 예를들면,,<br />노트북을 덮었다 열면 한 시간이 밀려 있는데, 그걸 다 따라잡으려고 이벤트 루프를 막아버린다(death spiral)</p>
<p data-ke-size="size16"><br /><code>MAX_CATCHUP</code>(5틱) 상한을 두고 그 이상은 현재 시점으로 점프하게 했다.</p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>교훈</b>: 게임 루프는 <i>시계가 튀는 상황</i>(슬립/복귀)을 가정해야 한다.</p>
<h3 data-ke-size="size23">입력 모델: State vs Event</h3>
<p data-ke-size="size16">입력을 "지금 누르고 있는 키 상태"(State, A)로 보낼지 "키 이벤트"(Event, B)로 보낼지. FPS는 거의 (A).</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>패킷 손실에 강하다. 한두 개 잃어도 다음 입력이 "현재 상태"를 가져온다.</li>
<li>서버 처리가 단순하다. "이 틱에 W가 눌려 있나"만 본다.</li>
<li><code>seq</code>(시퀀스 번호)로 <i>어디까지 처리했는지</i> 추적 &rarr; reconciliation의 기반.</li>
</ul>
<p data-ke-size="size16"><b>함정</b>: 입력 없는 틱은 <i>정지*로 처리된다. 그래서 클라이언트는 키를 안 눌러도 *매 틱 입력을 보내야</i> 한다.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">4. R3F 프론트 (Step 7~9)</h2>
<h3 data-ke-size="size23">"카메라 위치를 setState로 갱신하지 말 것"</h3>
<p data-ke-size="size16">R3F의 핵심 원칙.<br />게임은 매 프레임 위치가 바뀌는데, <code>setState</code>로 했다간 매 프레임 re-render &rarr; 컴포넌트 트리 전체 reconcile &rarr; 재앙.</p>
<pre class="stylus"><code>// 안 됨: 매 프레임 re-render
const [pos, setPos] = useState(...)
useFrame(() =&gt; setPos(...))
<p>// 맞음: ref + useFrame로 직접 mutate
const ref = useRef()
useFrame(() =&gt; { ref.current.position.x += ... })</code></pre></p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>교훈</b>: 3D 씬 안의 모든 매 프레임 변화는 ref + useFrame로 직접 mutate.<br /><i>누가 있냐</i> 같은 드물게 바뀌는 것만 React state.</p>
<h3 data-ke-size="size23">PointerLock의 SecurityError (뒤로가기 함정)</h3>
<p data-ke-size="size16">페이지를 하위 라우트로 만든 뒤 뒤로가기를 누르니 터졌다.</p>
<pre class="routeros"><code>SecurityError: Pointer lock cannot be acquired immediately after the user has exited the lock.</code></pre>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16">브라우저는 PointerLock에서 빠져나간 직후(약 1.25초) 재잠금을 막는다!<br />컨트롤이 remount되며 이전 lock 상태를 복원하려다 발생.<br />치명적이진 않지만 콘솔이 더러워진다.</p>
<p data-ke-size="size16"><br />&rarr; 그 종류의 <code>unhandledrejection</code>만 골라 <code>preventDefault</code>하는 핸들러로 무시.</p>
<h3 data-ke-size="size23">Strict Mode 이중 마운트 &rarr; store 초기화로 회피</h3>
<p data-ke-size="size16">Next dev의 React Strict Mode가 컴포넌트를 <i>두 번 마운트*한다.<br />WebSocket 연결이 두 번 되면서, 본인이 자기 자신을 "남"으로 인식해 *자기 박스가 빨갛게 보이는</i> 버그가 났다.</p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16">근본 원인은 따로 있었다(이어지는 내용 참고...)<br />하지만 이 과정에서 배운 건: <b>연결 시작 전에 게임 store를 초기화</b>하고, cleanup에서 확실히 정리하는 습관.</p>
<h3 data-ke-size="size23">"본인이 자기를 RemotePlayer로 그리는" 버그</h3>
<p data-ke-size="size16">처음엔 props를 안 넘겨서인 줄 알았다.<br />진짜 원인은 <b>welcome 도착 전에 첫 스냅샷이 처리되는 race</b>.</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>welcome이 오기 전 <code>myPlayerId</code>는 null.</li>
<li>그 사이 도착한 스냅샷의 본인을 "남"으로 분류 &rarr; RemotePlayer로 렌더.</li>
</ul>
<p data-ke-size="size16"><b>수정</b>: <code>myPlayerId</code>가 아직 없으면(welcome 전이면) 아무도 렌더하지 않는다.</p>
<pre class="gauss"><code>if (!snap || !myId) { if (otherIds.length) setOtherIds([]); return }</code></pre>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>교훈</b>: 내 추측("props 문제 아닐까")은 <i>증상</i>은 맞게 짚었지만 <i>원인</i>은 타이밍이었다. 비동기 메시지 순서를 항상 의심하자.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">5. 보간 (Step 10)</h2>
<h3 data-ke-size="size23">"늦게 그리는 게 부드럽다"</h3>
<p data-ke-size="size16">가장 비직관적인 핵심.<br />스냅샷이 66ms마다 오니까 도착하자마자 그 위치로 점프하면 뚝뚝 끊긴다.<br />해결은 <b>렌더링을 고의로 100ms 늦춰서 항상 두 스냅샷 사이를 보간</b>.</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>항상 <i>최신 스냅샷보다 100ms 뒤</i>를 그린다.</li>
<li>그 시점은 이미 도착한 두 스냅샷 사이 &rarr; 보간 가능.</li>
<li>패킷 한두 개 분실해도 버퍼에 다음 게 있어 끊기지 않는다.</li>
</ul>
<p data-ke-size="size16"><b>100ms를 고른 이유: 스냅샷 간격 66ms의 약 1.5배. 너무 크면(500ms) 남의 행동이 반 초 늦게 보인다.</b></p>
<h3 data-ke-size="size23">lerpAngle 함정</h3>
<p data-ke-size="size16">yaw가 &minus;&pi;에서 &pi;로 넘어가는 순간 일반 lerp를 쓰면 <i>반대 방향으로 한 바퀴</i> 돈다. 짧은 경로를 택하는 각도 보간이 필요하다.</p>
<p data-ke-size="size16"><b>교훈</b>: 본인은 보간하지 않는다. 본인까지 100ms 늦추면 <i>자기 입력에 100ms 지연 반응</i>하게 됨.<br /><b>본인은 예측(다음 단계), 남은 보간.</b></p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">6. 예측 + Reconciliation (Step 11)</h2>
<p data-ke-size="size16">가장 까다로운 단계.<br />클라이언트가 입력 즉시 자기 시뮬을 돌리고, 서버 스냅샷이 오면 <i>그 시점 이후 입력들을 재시뮬</i>한다.</p>
<h3 data-ke-size="size23">결정론 접근이 필요</h3>
<p data-ke-size="size16">예측과 재시뮬이 일치하려면 <b>클라이언트와 서버가 같은 시뮬 코드</b>여야 한다!<br /><code>stepPlayer</code>를 양쪽에 복사했다. 그리고:</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>dt 통일</b>: 클라가 1/60, 서버가 1/30이면 reconcile 때 <i>항상 보정</i>이 들어온다. 둘 다 1/30.</li>
<li><b>yaw 부호</b>: 회전식 부호 하나가 어긋났더니 reconcile 점프가 <i>영구적</i>으로 남았다. 두 함수를 나란히 놓고 한 글자씩 비교해야 했다.</li>
</ul>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">yaw 좌표계 함정<br />초반에 서버 회전식을 three.js 카메라 yaw와 안 맞게 짰다.<br />프론트 붙기 전엔 테스트가 yaw=0만 보내서 안 드러났다.<br /><b>교훈: 좌표계 검증은 yaw=0뿐 아니라 yaw=&pi;/2도 같이 해야 한다.</b></p>
</blockquote>
<h3 data-ke-size="size23">디버그 토글의 가치</h3>
<p data-ke-size="size16">"예측 ON/OFF"를 P 키로 토글하게 만들었다.<br />끄면 서버 권위만으로 끊기는 상태(Step 9), 켜면 부드러움.</p>
<p data-ke-size="size16"><br />토글하며 <i>예측과 서버 결과가 진짜 일치하는지</i> 검증했다.<br />이 토글이 디버깅 과정에서 정말 유용했다.</p>
<h3 data-ke-size="size23">30Hz stutter - 시뮬과 렌더 빈도의 차이</h3>
<p data-ke-size="size16">P키로 예측을 켜보니 <i>마우스 시점은 부드러운데 WASD 이동만 덜컥</i>거렸다.<br /><b>원인: 시뮬은 30Hz로만 위치를 갱신하는데 화면은 60fps!!</b></p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>해결</b>: 매 시뮬 틱의 직전 위치를 저장하고,<br />매 렌더 프레임에 <i>직전&rarr;현재 사이를 보간</i>(<code>getRenderPosition</code>). 다음 틱까지 남은 시간 비율로 lerp.</p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>교훈</b>: *"렌더 빈도와 시뮬 빈도는 다르고, 그 둘을 잇는 게 보간"*.</p>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">Glenn Fiedler의 "Fix Your Timestep!"이 이 주제의 표준 글.</p>
</blockquote>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">7. Rapier 물리 (Step 12)</h2>
<p data-ke-size="size16">클라/서버 양쪽에 Rapier를 도입해 충돌&middot;점프&middot;중력을 넣었다.<br />서브스텝으로 나눠 진행: 서버 도입 &rarr; 클라 도입(예측 일치) &rarr; 점프/중력 &rarr; 박스/닉네임 마무리.</p>
<h3 data-ke-size="size23">cuboid는 반 크기, boxGeometry는 전체 크기</h3>
<p data-ke-size="size16">가장 자주 틀린 실수.<br />박스 위로 점프가 안 올라가져서 한참 봤더니, 시각 박스만 줄이고 <i>물리 콜라이더는 그대로 2m 높이</i>였다.</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><code>ColliderDesc.cuboid(1, 1, 1)</code> &rarr; 전체 (2, 2, 2)</li>
<li><code>&lt;Box args={[2, 2, 2]}&gt;</code> &rarr; 전체 (2, 2, 2)</li>
</ul>
<p data-ke-size="size16">콜라이더 반 크기 N을 정했으면 시각 박스 args는 2N, 위치는 바닥에 붙이려면 중심을 N만큼 올린다.</p>
<h3 data-ke-size="size23">KinematicCharacterController</h3>
<p data-ke-size="size16">캐릭터는 <code>kinematicPositionBased</code> body + <code>KinematicCharacterController</code>.<br />동역학(dynamic) body로 만들면 마찰&middot;미끄러짐&middot;회전이 골치 아프다.<br />키네마틱은 <i>위치를 코드로 정밀 제어</i>한다.</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><code>computeColliderMovement(collider, desiredDelta)</code> &rarr; 충돌 고려한 실제 이동 계산(슬라이딩&middot;경사&middot;계단 자동)</li>
<li><code>setNextKinematicTranslation</code> &rarr; 다음 <code>world.step()</code>에 반영. <b><code>setTranslation</code>(즉시)과 헷갈리지 말 것.</b></li>
</ul>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">중력은 자동이 아니다<br />World에 중력 벡터를 줘도 <b>kinematic body는 중력 영향을 안 받는다.</b><br />이건 dynamic만 받는다. vy(수직 속도)를 매 틱 직접 적분해야(계산해줘야..) 한다.</p>
</blockquote>
<h3 data-ke-size="size23">캐릭터끼리 통과: sensor 단독으론 안 된다</h3>
<p data-ke-size="size16">플레이어끼리 부딪히지 않고 통과하게 만들려고 캡슐을 <code>setSensor(true)</code>로 했는데 <b>여전히 막혔다</b>.</p>
<p data-ke-size="size16">캐릭터 컨트롤러는 물리 시뮬과 별개 알고리즘이라 sensor도 기본적으로 장애물로 본다.</p>
<p data-ke-size="size16"><br /><code>computeColliderMovement</code>에 <code>QueryFilterFlags.EXCLUDE_SENSORS</code>를 <i>함께</i> 줘야 풀린다.</p>
<pre class="css"><code>controller.computeColliderMovement(collider, delta, RAPIER.QueryFilterFlags.EXCLUDE_SENSORS)</code></pre>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>교훈</b>: sensor 플래그와 EXCLUDE_SENSORS 필터는 한 묶음으로 동작한다.</p>
<h3 data-ke-size="size23">리스폰 위치가 안 바뀌던 버그</h3>
<p data-ke-size="size16">사망 시 <code>setNextKinematicTranslation</code>으로 새 위치를 줬는데 <i>그 자리에 그대로</i> 다시 생겼다.<br />setNext는 <i>다음 step</i>에 반영되는데, 그 사이 stepPlayer가 옛 위치 기준으로 계산해 거의 안 움직였다.<br /><b>&rarr; 즉시 반영되는 <code>setTranslation(pos, true)</code>로 교체~!</b></p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">8. 사격 &mdash; 페인트볼 (Step 13)</h2>
<h3 data-ke-size="size23">포물선으로 갈 것</h3>
<p data-ke-size="size16">직선이면 "느린 총알" 느낌. 페인트볼의 본질은 <i>중력 받는 투사체</i>.<br />이미 중력 시스템이 있으니 vy 적분 코드를 그대로 재활용했다.<br />초기 속도 30m/s + 중력 &minus;9.8이면 가까운 거리는 거의 직선, 멀수록 떨어져서 <i>조준의 재미</i>가 생긴다.</p>
<h3 data-ke-size="size23">raycast가 아니라 segment cast (터널링 방지)</h3>
<p data-ke-size="size16">투사체가 빠르면(30m/s &times; 1/30s = 1m/틱) <i>한 틱에 벽을 통과*해버린다?(터널링).<br />그래서 매 틱 *직전 위치 &rarr; 현재 위치</i> 선분을 raycast로 검사했다.<br /><code>world.castRay(ray, maxToi=거리)</code>.</p>
<h3 data-ke-size="size23">castRay의 predicate로 자기 자신 제외</h3>
<p data-ke-size="size16">페인트볼이 자기 캡슐 안에서 출발하니 <i>발사 즉시 자기 사망</i>이 될 수 있다.<br />raycast 필터로 발사자 콜라이더를 제외했다(<code>filterExcludeCollider</code> 또는 predicate 콜백).</p>
<h3 data-ke-size="size23">InstancedMesh의 frustumCulled 함정</h3>
<p data-ke-size="size16">페인트볼 64개를 <code>InstancedMesh</code>(한 draw call)로 그렸다.<br />그런데 <b>외곽 방향으로 쏘면 본인 화면에서만 안 보였다</b>.</p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16">원인: InstancedMesh의 boundingSphere는 <i>원본 geometry 기준</i>(원점의 작은 구)이라, 카메라가 원점을 안 보면 InstancedMesh 전체가 <b>frustum culling</b>되어 통째로 안 그려진다(!)</p>
<p data-ke-size="size16"><br />실제 인스턴스는 눈앞에 있는데도. 이거 찾는데 힘들었따...</p>
<p data-ke-size="size16"><b>&rarr; <code>frustumCulled={false}</code> 한 줄로 해결</b></p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>교훈</b>: 일반 mesh는 자동으로 잘 되는데 InstancedMesh는 위치가 인스턴스 행렬에 들어있어 부모 bounding이 안 맞는다.<br />잘 알려진 함정이라는데,, 처음 겪으면 한참 헤맨다.</p>
<h3 data-ke-size="size23">어두운 쪽에서 안 보이던 것 &mdash; 사실은 culling</h3>
<p data-ke-size="size16">"어두운 방향으로 쏘면 안 보인다"고 처음 진단했지만, 실은 위 culling이 <i>어두운 외곽과 자주 겹쳐서</i> 그렇게 보였던 것.</p>
<p data-ke-size="size16">material을 <code>meshBasicMaterial</code>(빛 무시)로 바꾼 건 손전등 컨셉상 옳은 선택이었지만, 진짜 원인은 culling이었다.</p>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16"><b>교훈</b>: 증상의 표면(어둠)과 실제 원인(culling)을 혼동하지 말 것. <i>조건을 하나씩 격리</i>해야 한다.</p>

<h2 data-ke-size="size26">10. 시각 컨셉 &mdash; 손전등 (Step 16)</h2>
<p data-ke-size="size16">씬을 거의 검정으로 낮추고(ambient 0.02~0.05, 약한 fill), 카메라에 SpotLight를 부착했다.</p>
<h3 data-ke-size="size23">SpotLight를 카메라에 add - 본인 빔이 안 보이던 이유</h3>
<p data-ke-size="size16">다른 사람 손전은 보이는데 <i>본인 손전등만 안 보였다</i>. 두 가지가 겹친 현상:</p>
<ol style="list-style-type: decimal;" data-ke-list-type="decimal">
<li>손전등이 <b>완전 수평</b>으로 비추면 평지엔 닿지 않는다. 30m 직선으로 벽에 닿는데 그 벽이 어둠 멀리 있어 빔 영향이 미미.</li>
<li>광원이 카메라 안쪽에 있어 빔의 측면을 못 본다.</li>
</ol>
<p data-ke-size="size16">&rarr; <b>손전등 target의 y를 음수로</b> 해서 <i>살짝 아래로</i> 비추게 했다(<code>target.position.set(0, -0.5, -1)</code>).<br />발 앞 바닥이 환해지며 손전 효과가 명확해졌다. + intensity&middot;distance&middot;angle 강화.</p>
<p data-ke-size="size16"><b>교훈</b>: <i>빛을 받는 표면이 있어야</i> 보인다. 광원만 켰다고 보이는 게 아니다.</p>
<h3 data-ke-size="size23">RemotePlayer 손전이 yaw를 안 따르던 것</h3>
<p data-ke-size="size16">다른 사람 손전이 항상 바닥으로만 향했다.<br />SpotLight target을 group 자식으로 두니 <b>target의 worldMatrix 갱신 타이밍</b> 문제로 회전이 누락됐다.</p>
<p data-ke-size="size16">&rarr; target을 <b>씬에 직접 추가</b>하고, useFrame에서 <b>플레이어 yaw를 forward 벡터로 변환</b>해 씬 절대 좌표로 매 프레임 직접 설정. 회전 누락이 사라졌다.</p>
<pre class="arduino"><code>const forwardX = -Math.sin(yaw)  // -Z가 forward
const forwardZ = -Math.cos(yaw)
target.position.set(x + forwardX, headY - 0.3, z + forwardZ)</code></pre>

<h2 data-ke-size="size26">11. 여기까지 함정 모음</h2>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>30Hz stutter</b>: 시뮬 빈도와 렌더 빈도가 달라 발생 &rarr; 두 시뮬 틱 사이 보간(<code>getRenderPosition</code>).</li>
<li><b>yaw 좌표계 부호</b>: 클라이언트/서버 회전식 한 글자 차이 &rarr; reconcile 영구 점프. yaw=&pi;/2까지 검증.</li>
<li><b>Next.js hydration mismatch</b>: <code>Math.random()</code> 닉네임이 SSR/CSR에서 달라짐 &rarr; 게임 페이지를 <code>dynamic</code> + <code>ssr:false</code>로 통째 클라 전용.</li>
<li><b>React Hook 순서 위반</b>: 조건부 return 뒤 useEffect &rarr; 모든 훅을 상단에.</li>
<li><b>InstancedMesh culling</b>: boundingSphere가 원본 geometry 기준 &rarr; <code>frustumCulled={false}</code>.</li>
<li><b>SpotLight target 누락/타이밍</b>: target도 씬 또는 카메라 자식이어야 하고, 회전이 누락되면 씬에 직접 두고 매 프레임 갱신.</li>
<li><b>sensor vs 캐릭터 컨트롤러</b>: sensor 단독으론 컨트롤러가 안 풀림. <code>EXCLUDE_SENSORS</code> 같이 필요.</li>
<li><b>cuboid 반 크기 vs boxGeometry 전체 크기</b>: 가장 흔한 단위 혼동.</li>
<li><b>setNextKinematicTranslation vs setTranslation</b>: 리스폰 같은 <i>즉시</i> 이동은 setTranslation.</li>
<li><b>kinematic body는 중력 안 받음</b>: vy 직접 적분.</li>
<li><b>welcome 전 스냅샷 race</b>: myPlayerId 없으면 아무도 렌더 안 함.</li>
