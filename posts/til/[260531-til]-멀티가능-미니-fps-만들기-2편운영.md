<h1>멀티플레이어 미니 FPS 만들기 2편(운영편)</h1>
<h2 data-ke-size="size26">전체 흐름</h2>
<pre class="armasm"><code>코드 정리(상수 중앙화) &rarr; 멀티룸(로비) &rarr; EC2 배포 &rarr; 맵 권위화 &rarr; 자연 지형 &rarr; 아레나 확장 &rarr; 밤하늘 &rarr; rubber-banding 진단</code></pre>
<p data-ke-size="size16">&nbsp;</p>
<p data-ke-size="size16">진행 방식이 기본편과 달랐다. <a href="https://ifelseif.tistory.com/346" target="_blank" rel="noopener">기본편 보러가기</a><br />기본편 단계에서는 한 단계씩 내가 직접 검증하며 구현했고,</p>
<p data-ke-size="size16">여기는 클로드코드로 에이전트 파이프라인(architect &rarr; implementer &rarr; reviewer &rarr; qa)으로 굵직한 작업 단위를 처리했다.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">Part 1 - 상수/매직넘버 중앙화</h2>
<h3 data-ke-size="size23">무엇 / 왜</h3>
<p data-ke-size="size16">서버 전반에 흩어진 매직넘버를 단일 소스로 모았다. 핵심은 <b>숨은 결합</b>을 드러내는 것.<br />예를 들어 틱 레이트 <code>TICK_HZ=30</code>과 물리 <code>timestep=1/30</code>은 <i>반드시 같아야</i> 하는데 따로 떨어져 있었다.<br />스폰 높이 <code>0.9</code>도 여기저기 퍼져 있었다.</p>
<h3 data-ke-size="size23">핵심 변경</h3>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><code>src/config.ts</code> 신설(도메인별 섹션). 8개 모듈이 여기서 import.</li>
<li>파생값으로 결합 명시: <code>TICK_INTERVAL_S</code> 파생, <code>PLAYER_SPAWN_Y = 캡슐반높이 + 반지름</code>.</li>
<li>정체불명 매직넘버에 이름 부여(머즐 오프셋&middot;킬플레인&middot;접지속도 등).</li>
<li>벽/박스 좌표를 <code>ARENA_SIZE</code> 기반 계산으로.</li>
<li>값은 동일 &rarr; <b>동작 변화 없음</b>.</li>
</ul>
<h3 data-ke-size="size23">교훈</h3>
<p data-ke-size="size16">상수 중앙화의 진짜 가치는 "한 곳에서 바꾸기"보다 <b>암묵적 결합을 코드로 명시하는 것</b>.<br /><code>timestep = TICK_INTERVAL_S</code>처럼 <i>파생관계로 적으면</i> 둘이 어긋날 수 없다.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">Part 2 - 로비: 방 목록/생성/입장 (멀티룸)</h2>
<h3 data-ke-size="size23">무엇 / 왜</h3>
<p data-ke-size="size16">접속 즉시 단일 default 룸 자동 입장이던 걸 <b>로비 단계</b>로 바꿨다.<br />방 목록 확인 &rarr; 생성(최대 3개) 또는 입장 &rarr; 게임 진입.<br />목록은 서버 push로 실시간 갱신.</p>
<h3 data-ke-size="size23">핵심 변경</h3>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>프로토콜</b>: <code>hello</code>를 신원 등록만으로 축소(자동 입장 제거). C&rarr;S <code>list_rooms</code>/<code>create_room</code>/<code>join_room</code>/<code>leave_room</code>, S&rarr;C <code>room_list</code>/<code>room_joined</code>/<code>room_left</code> 추가. <code>welcome</code>에서 peers 제거(룸 입장 시점으로 이동).</li>
<li><b>서버</b>: <code>Hub</code>가 로비/방 라우팅, <code>MAX_ROOMS=3</code>, 빈 방 자동 폐기 + 방 번호 재사용, 변동 시 로비 클라이언트에 <code>room_list</code> push.</li>
<li><b>프론트</b>: <code>Session</code> 컴포넌트(연결&middot;물리초기화&middot;phase 라우팅)가 기존 <code>NetBridge</code>를 대체. <code>useSyncExternalStore</code> 로비 스토어. <code>Lobby</code> UI(실시간 N/3, 가득참/생성제한 처리).</li>
</ul>
<h3 data-ke-size="size23">교훈</h3>
<p data-ke-size="size16">phase(로비 &harr; 게임)가 생기면서 <i>연결 라이프사이클</i>과 <i>게임 라이프사이클</i>을 분리해야 했다.<br /><code>Session</code>이 그 경계를 맡으면서 컴포넌트 책임이 명확해졌다.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">Part 3 - game-server를 EC2에 통합 배포</h2>
<h3 data-ke-size="size23">무엇 / 왜</h3>
<p data-ke-size="size16">game-server(WS)를 EC2에 컨테이너로 띄우고 <code>wss://domain/fps</code>로 노출.<br />(EC2에 이미 떠있는 리소스와 독립 배포)</p>
<blockquote data-ke-style="style1">
<p data-ke-size="size16">기본편 초반의 결정("EC2를 재활용하되 Nest는 아님")이 여기서 결실.<br />같은 박스, 다른 프로세스/컨테이너.</p>
</blockquote>
<h3 data-ke-size="size23">핵심 변경</h3>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><code>game-server/Dockerfile</code>(arm64 멀티스테이지, ESM <code>type:module</code>, <code>EXPOSE 4000</code>).</li>
<li><code>deploy/ec2/compose.yml</code>에 <code>game-server</code> 서비스 추가(127.0.0.1:4000, 독립 ECR/IMAGE_TAG).</li>
<li>Nginx <code>location /fps</code> WebSocket 프록시(Upgrade 헤더 + 긴 타임아웃).</li>
<li><code>terraform</code>에 game 전용 ECR 레포 + 출력.</li>
<li><code>scripts/deploy-game-ec2.sh</code> 신설, 기존 <code>deploy-ec2.sh</code>를 서비스 한정으로 공존 처리.</li>
<li>프론트 프로덕션: <code>NEXT_PUBLIC_GAME_WSS_URL=wss://domain/fps</code>.</li>
</ul>
<h3 data-ke-size="size23">교훈</h3>
<p data-ke-size="size16">WebSocket은 Nginx에서 <b>Upgrade 헤더 처리 + 타임아웃 연장</b>이 필수.<br />일반 HTTP 프록시 설정 그대로 두면 핸드셰이크는 되는데 연결이 금방 끊긴다.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">Part 4 - 인프라 안전장치 (terraform)</h2>
<p data-ke-size="size16">배포하면서 <b>지뢰 두 개</b> 밟을 뻔했다.</p>
<h3 data-ke-size="size23">ECR 라이프사이클</h3>
<p data-ke-size="size16">기존 정책이 태그 prefix <code>v</code> 기준이라 <b>git-sha 태그 이미지가 만료가 안 됐다</b>.<br />계속 쌓여서 디스크 누적. &rarr; <code>tagStatus="any"</code>로 최신 N개(기본 10)만 유지 + untagged 1일 후 만료.</p>
<h3 data-ke-size="size23">EC2 강제 교체 방지</h3>
<p data-ke-size="size16"><code>data "aws_ami" most_recent=true</code> + <code>aws_instance.ami</code> 조합은 <b>새 AMI 출시 시 인스턴스를 destroy+recreate</b> 한다.<br />모르고 apply하면 운영 인스턴스가 날아간다... <b>이거 놓쳐서 실제로 날아갔다.. 개인 프로젝트였기에 망정이지..</b><br />&rarr; <code>lifecycle { ignore_changes = [ami, user_data] }</code></p>
<h3 data-ke-size="size23">운영 수칙 재확인...</h3>
<blockquote data-ke-style="style1">
<p data-ke-size="size16"><code>terraform apply</code> 전에 항상 <code>terraform plan</code>으로 <b><code>0 to destroy</code></b> 확인.</p>
</blockquote>
<h3 data-ke-size="size23">교훈</h3>
<p data-ke-size="size16">IaC의 무서운 점은 <i>의도치 않은 destroy</i>. ㅜㅜㅜㅜ<br /><code>most_recent=true</code> 같은 "항상 최신" 옵션이 <b>멱등을 깨는</b> 함정이 됨.</p>
<hr data-ke-style="style1" />
<h2 data-ke-size="size26">Part 5 - 맵을 서버 권위 데이터로 (가장 영향 큰 리팩토링)</h2>
<h3 data-ke-size="size23">무엇 / 왜</h3>
<p data-ke-size="size16">프론트가 맵 지오메트리를 <b>3겹으로 복붙</b> 보유하던 구조를 제거했다.</p>
<ol style="list-style-type: decimal;" data-ke-list-type="decimal">
<li>렌더용 메시(Arena.tsx)</li>
<li>예측용 Rapier 충돌</li>
<li>물리 상수</li>
</ol>
<p data-ke-size="size16">세 곳이 각각 맵을 알고 있어서, 맵을 바꾸려면 세 곳을 동시에 수정해야 했다(기본편 내내 "양쪽 동시 수정" 했었다...)</p>
<p data-ke-size="size16"><b>&rarr; 서버가 맵을 단일 권위로 정의해 JSON 전송. 프론트는 그 데이터로 렌더 메시와 예측 Rapier 월드를 모두 구성</b></p>
<h3 data-ke-size="size23">핵심 변경</h3>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>서버 <code>src/map.ts</code>(<code>MapDefinition</code> + <code>DEFAULT_MAP</code> + <code>buildWorldColliders</code>), <code>physics.ts</code>가 맵 데이터로 월드 구성(하드코딩 제거), <code>protocol.ts</code>에 <code>MapDefinition</code>/<code>room_joined.map</code>, 입장 시 map 동봉.</li>
<li>프론트 <code>createClientWorld(map)</code>/<code>prediction.setup(map)</code>, <code>arena.tsx</code>가 map으로 렌더, <code>config/arena.ts</code> 삭제, 진입 시 <code>MapLoading</code> 가드.</li>
<li>스키마 <code>version</code> 검증, <code>terrain</code> 슬롯 전방호환 예약.</li>
</ul>
<h3 data-ke-size="size23">검증</h3>
<p data-ke-size="size16">서버에서 맵 위치 한 곳만 바꾸면 <b>클라이언트는 무수정으로</b> 렌더+충돌이 둘 다 따라옴 = SSOT 전환 성공.</p>
<h3 data-ke-size="size23">교훈</h3>
<p data-ke-size="size16"><b>이 리팩토링이 이후 모든 것을 가능하게 했다.</b><br />Part 6(자연 지형)도 Part 8(아레나 3배 확장)도 <i>서버 한 곳만 수정</i>하면 됐다.<br />권위 데이터를 일찍 분리한 효과.</p>

<h2 data-ke-size="size26">Part 6 - 자연 지형 (heightfield)</h2>
<h3 data-ke-size="size23">무엇 / 왜</h3>
<p data-ke-size="size16">평지를 부드러운 굴곡 지형으로. <i>시각만이 아니라 충돌도</i> 지형을 따른다.</p>
<h3 data-ke-size="size23">핵심 변경</h3>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>서버 <code>map.ts</code>: 저주파 사인 합 + 가장자리 falloff로 지형 생성 &rarr; <code>MapDefinition.terrain</code>(정점 그리드). <code>buildWorldColliders</code>가 Rapier <code>heightfield</code> 콜라이더 생성. <code>terrainHeightAt</code>(양선형 샘플러) + <code>spawnYAt</code>로 스폰/리스폰/장애물을 지형 표면에 안착.</li>
<li>프론트: 예측 월드에 동일 heightfield, <code>BufferGeometry</code> 메시 렌더(콜라이더와 동일 인덱스&rarr;월드 매핑).</li>
</ul>
<h3 data-ke-size="size23">검증 - probe로 API 실측</h3>
<p data-ke-size="size16">Rapier heightfield API를 추측하지 않고 <b>실측 probe로 확정</b>했다:<br />배열 길이 <code>(rows+1)*(cols+1)</code>, 인덱스 <code>ix*(cols+1)+iz</code>, 원점 중심.<br />그 다음 <b>서버 충돌 raycast &harr; 샘플러를 비교해 diff 0.00</b> 확인 &rarr; 시각 메시와 물리가 정렬됨을 보장.</p>
<h3 data-ke-size="size23">교훈</h3>
<p data-ke-size="size16"><b>문서가 모호한 API는 추측 말고 probe</b><br />heightfield의 정점 배열 레이아웃은 라이브러리마다 다르고, 한 칸만 어긋나도 시각과 충돌이 따로 논다.<br />작은 probe 스크립트로 수 시간을 아꼈다.</p>

<h2 data-ke-size="size26">Part 9 - Rubber-banding 진단 (가장 배운 게 많은 디버깅)</h2>
<h3 data-ke-size="size23">증상</h3>
<p data-ke-size="size16">배포 환경에서 점프&middot;이동 시 화면이 "살짝 되돌아갔다 복귀"를 빠르게 반복(rubber-banding).<br />지형 도입 후 증상 발생. <b>로컬(저지연)에선 무증상</b> &rarr; <b>지연이 트리거 였다!</b></p>
<h3 data-ke-size="size23">진단 방법론 &mdash; differential harness</h3>
<p data-ke-size="size16">시각 회귀로 디버깅하면 답이 없다...<br /><b>서버 truth 시뮬(연속)과 클라이언트식 시뮬(지연 + reconcile 재시뮬)을 나란히 돌려 발산 크기를 숫자로 측정</b>하는 harness를 만들었다.</p>
<h3 data-ke-size="size23">근본 원인</h3>
<p data-ke-size="size16"><code>reconcile</code>이 <b>위치만 복원하고 <code>vy</code>/<code>grounded</code>(물리 동역학 상태)는 복원 안 함</b>.<br />그래서 재시뮬 시작 상태가 매 스냅샷 달라져 궤적이 발산.</p>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li>평지에선 vy가 &minus;1로 수렴해 무해.</li>
<li>지형 경사/점프에서 발산.</li>
<li>vy까지 복원하니 harness 발산이 <b>2.8m &rarr; 0.000</b>으로 떨어져 원인 확정.</li>
<li>(heightfield 비결정성 가설은 이 과정에서 기각.)</li>
</ul>
<h3 data-ke-size="size23">잔여 점프 증상</h3>
<p data-ke-size="size16">배포(실지연)에서만 남는 미세 점프.<br />SSM 로그로 <b>서버 틱 드리프트 0</b> 확인(EC2 부하 아님, 처음엔 EC2 부하인줄로만 알았다...)<br /><b>코드는 지연 무관 결정적</b>임을 확인하고, <b>점프 발동 시 grounded 경계 판정이 클라이언트/서버 간 위상차</b> 날 때만 발생함을 격리.</p>
<h3 data-ke-size="size23">수정 (3종 세트)</h3>
<ol style="list-style-type: decimal;" data-ke-list-type="decimal">
<li><b>vy/grounded 동기화</b>: 서버 스냅샷에 본인 전용 <code>yourVy</code>/<code>yourGrounded</code> 추가 &rarr; 클라이언트 reconcile에서 복원(구버전 서버 하위호환 폴백 포함).</li>
<li><b>coyote-time</b> (<code>COYOTE_TIME_S=0.08</code>): 지면 떠난 직후 짧게 점프 허용 &rarr; grounded 경계 위상차 감소. <b>클라이언트&middot;서버 동일 로직 미러</b>(예측 일치 필수).</li>
<li><b>reconciliation smoothing</b>: 보정을 즉시 스냅 대신 <code>errorOffset</code>에 담아 렌더에서 80ms 지수 감쇠로 흡수. 2m 초과(리스폰)는 즉시 스냅.</li>
</ol>
<h3 data-ke-size="size23">교훈</h3>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>결정론 시뮬에선 위치 외의 동역학 상태(vy&middot;grounded)도 reconcile 대상</b>이다. 기본편에서 "vy/grounded는 자연 수렴하니 둔다"고 했던 게, 평지에선 맞았지만 지형에선 틀렸다.</li>
<li><b>시각이 아니라 숫자로 보는 디버깅</b>(differential harness). 가설 검증과 기각이 명확히 분리될 때 좋은 진단이 된다.</li>
<li>로컬 무증상 / 배포 유증상 &rarr; <i>지연이 트리거인 결정론 버그</i>를 의심.</li>
</ul>

<h2 data-ke-size="size26">핵심 아키텍처 개념 (재정리)</h2>
<ul style="list-style-type: disc;" data-ke-list-type="disc">
<li><b>서버 권위 + 클라이언트 예측</b>: 서버 30Hz 시뮬(진실), 클라이언트 입력 즉시 예측 + 서버 스냅샷(15Hz) reconcile. 예측&middot;재시뮬 일치를 위해 시뮬 로직(이동&middot;중력&middot;점프&middot;coyote)과 충돌 지오메트리(Rapier 동일 버전&middot;동일 맵)가 <b>결정론적으로 동일</b>해야.</li>
<li><b>단일 권위 데이터(MapDefinition)</b>: 맵을 서버가 정의&middot;전송 &rarr; 렌더&middot;충돌&middot;예측이 한 소스에서 파생. 복붙 제거가 이후 모든 월드 변경을 서버 1곳 수정으로 가능하게 한 핵심.</li>
<li><b>배포</b>: 단일 EC2 + docker compose(backend/game-server) + 호스트 Nginx 경로 분기(<code>/</code>&rarr;3000, <code>/fps</code>&rarr;4000 WS). 두 서비스 독립 ECR&middot;독립 배포.</li>
</ul>
